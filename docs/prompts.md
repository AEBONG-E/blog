> 상황별로 복사해서 사용한다. `{ }` 부분만 바꿔 넣는다.
> 모든 프롬프트는 기본지침(프로젝트 문서 `claude/01_기본지침.md`)을 전제로 한다.

## P1. 초기 세팅 — 프로젝트 뼈대 생성 (1회)

```
기본지침과 작업 진행 계획의 Phase 1을 진행해줘.

- 저장소 이름: {username}.github.io   ← 또는 {repo-name} (이 경우 basePath 설정 필요)
- Next.js App Router + MDX + output: 'export' 정적 빌드
- 페이지: 홈(최근 글), /posts 목록(카테고리 필터), /posts/[slug] 글 상세, /series/[id] 시리즈 목차
- 디자인·메인 구성은 기본지침 1.1 벤치마킹 규칙 준수 (참고 사이트와 유사하지 않게, 디자인 방향 2~3안 먼저 제안)
- 상태 라벨(status) 표시: 글 목록 카드·글 상세 제목 위에 색 라벨, 글 목록에 상태별 필터 (기본지침 5.2.1)
- 글 상세 하단에 "수정" 링크(/admin 해당 글 편집 화면으로 이동)
- 샘플 글 1개 (본문 템플릿 그대로)
- 기준 문서 커밋: docs/guidelines.md(01_기본지침 사본), docs/categories.md(04_카테고리 사본), docs/topic-history.md(빈 이력 표)
- GitHub Actions 배포 워크플로
- .gitignore에 .env 등 민감 파일 포함

결과물은 zip으로 묶어서 주고, 내가 직접 해야 할 일(저장소 생성, push, Pages 설정)을 순서대로 정리해줘.
```

## P3. 매일 초안 작성 (반복 사용)

```
오늘의 초안을 작성해줘.

- 주제: {주제}   ← 비워두면 04_카테고리.md 순환 순서의 다음 대분류에서 미작성 소분류 선택
- 카테고리: {language | database | framework | cs | architecture | devops | data | security | domain}
- 소분류: {소분류}   ← 04_카테고리.md 기준
- 시리즈: {series id / 순서}  (해당 시)
- 난이도: {입문 | 실무 | 면접 심화}

규칙:
- 기본지침 5.3 본문 템플릿 그대로 (기술 글 본문이 중심, 면접 연결은 7번 섹션에)
- status: 초안
- frontmatter의 subcategory는 04_카테고리.md 소분류 이름 그대로 채운다
- "직접 해본 것"은 TODO로 비워두고, 내가 실험해볼 만한 과제 2~3개만 제안
- 면접으로 연결하기: 질문이 나오는 흐름, 대표 질문과 답변 핵심 포인트(내 말 정리는 TODO), 예상 꼬리질문 3~5개
- 연계 학습: 선행 주제 / 심화 주제 (블로그에 있는 글이면 링크)
- 핵심 키워드 강조는 기본지침 5.6 표기를 따른다 (**키워드**, *보조 강조*, `코드`)
- 확실하지 않은 내용은 <!-- 확인 필요 --> 표시
- 참고 자료는 공식 문서/RFC 우선, 링크 포함
- 시각화가 효과적인 지점이 있으면 어떤 컴포넌트가 좋을지 제안만 (구현은 별도 요청 시)

완료되면 content/posts/{slug}.mdx 로 main에 직접 커밋하고(커밋 메시지: "post: {제목}"), docs/topic-history.md에 이력을 추가해줘.
```

## P4. 내가 수정한 글 검토 (선택)

```
content/posts/{slug}.mdx 를 내가 수정했어. 최신 파일 기준으로 검토해줘.

- 사실 오류, 오탈자만 지적 (문체·구조는 유지)
- 면접관이 이 글을 보고 물어볼 만한 질문 3개
- 내가 쓴 답변 중 설명이 부족한 부분
- 면접 연결 섹션(7번)이 본문 내용과 맞는지, 본문에 없는 내용이 면접 섹션에만 있지 않은지
- 수정 제안은 "변경 전 → 변경 후 → 이유" 형식으로
```

## P5. 시각화 컴포넌트 추가 (선택)

```
{slug} 글의 "{섹션명}"에 들어갈 인터랙티브 시각화를 만들어줘.

- 기본지침 5.5 시각화 규칙을 따른다
- 이미 있는 범용 컴포넌트(components/viz/)로 가능하면 새로 만들지 말고 MDX 데이터만 작성
- 새로 만들 경우: components/viz/{ComponentName}.tsx, 외부 라이브러리 추가 없이 React + SVG
- 화면 문구·단계·수치는 props로 받아 MDX에 작성 (컴포넌트에 하드코딩 금지)
- 단계 진행(다음/이전/초기화) 또는 비교 토글 형태
- 다크모드 대응, 모바일 폭에서 깨지지 않게
- 컴포넌트 코드는 PR로, MDX 데이터는 글과 함께 main 커밋
```

## P9. 시각화 동작·디자인 수정 요청 (수시)

> 문구·단계 설명 수정은 CMS에서 직접 한다. 이 프롬프트는 코드 수정이 필요할 때만 쓴다.

```
{slug} 글의 {ComponentName} 시각화를 수정해줘.

- 수정 내용: {예: 재전송 단계 추가 / 애니메이션 속도 조절 / 모바일에서 겹침 해결}
- 이 컴포넌트를 쓰는 다른 글이 있으면 영향 여부를 먼저 확인해줘
- 최신 파일 기준으로 최소 범위만 수정 (기본지침 6. 코드 변경 원칙)
- 브랜치 viz/{ComponentName}-{요약}으로 PR 생성
- PR 본문: 변경 파일 / 변경 내용 / 이유 / 영향 받는 글 목록
```

## P10. 규칙 변경 (수시)

> 항상 적용되어야 하는 규칙을 바꿀 때 쓴다 (기본지침 8장 A 분류). 일회성 수정에는 쓰지 않는다.

```
다음 규칙을 바꾸고 싶어: {변경하고 싶은 내용}

- 기본지침 8장 변경 관리 절차를 따른다
- 먼저 영향 받는 문서(기본지침, 04_카테고리, 02_프롬프트, 사이트 코드)를 찾고
  "변경 전 -> 변경 후 -> 이유" 형식으로 제안만 해줘. 승인 후 반영한다
- 승인되면 저장소 문서는 PR(브랜치 rule/{요약})로, Cowork 프로젝트 문서는 직접 수정하고
  각 문서 하단 변경 이력과 CHANGELOG.md에 한 줄씩 남겨줘
- 프로젝트 지침(고정 문구) 변경이 필요하면 제안만 해줘. 지침은 내가 직접 수정한다
```

