| 부가 목적 | 각 글의 끝에 그 주제가 면접 질문으로 이어지는 흐름, 답변 골격, 예상 꼬리질문, 연계 학습을 함께 정리 (이력서 링크용 포트폴리오) |

| 운영자 | 본인 1인 (저장소 쓰기 권한 단독 보유) |
 
### 1.1 벤치마킹 규칙
 
참고 사이트는 **아이디어와 구조만** 참고한다. 화면이 참고 사이트와 비슷해 보이지 않도록 한다.
 
| 참고 가능 (아이디어·구조) | 사용 금지 (표현·디자인) |
|---|---|
| 글 목록 → 글 상세 → 시리즈 목차 페이지 구성 | 메인 페이지 레이아웃, 문구, 슬로건 |
| 면접 질문 → 꼬리질문 → 설명 → 체크리스트 글 흐름 | 색상, 폰트 조합, 카드 디자인, 로고 |
| 단계 진행형 등 시각화의 형식 | 시각화 코드, 화면 구성, 예시 데이터 |
| 카테고리 필터, 시리즈 진행률 등 기능 | 섹션 이름·표현, 후기, 통계 수치, 아티클 본문 |
 
- 메인 페이지는 개인 학습·포트폴리오 목적에 맞게 구성한다 (최근 글, 카테고리, 상태별 현황 등). 뉴스레터·구독 유도형 랜딩은 만들지 않는다.
- 디자인(색, 타이포그래피, 레이아웃)은 독자적으로 정한다. 작업 중 참고 사이트의 소스·스타일·이미지를 가져오지 않는다.

## 3. 권한 원칙
 
| 대상 | 권한 |
|---|---|
| 본인 | 작성·수정·삭제·발행 (CMS 또는 GitHub) |
| 에이전트(Claude) | 글 작성 후 main에 직접 커밋 → 즉시 게시. `status: 초안`으로 작성 |
| 방문자 | 읽기 전용. `/admin` 접근 가능하나 저장소 쓰기 권한 없으므로 수정 불가 |
 
- 글(콘텐츠)은 PR 없이 main에 직접 커밋한다. 게시 후 본인이 CMS에서 언제든 수정한다.
- 에이전트가 PR 없이 바꿀 수 있는 경로는 `content/posts/`, `public/images/posts/`, `docs/topic-history.md`로 한정한다.
- 사이트 소스(컴포넌트, 설정, 배포 워크플로, `public/admin/`)는 PR로 검토 후 반영한다.
- `완료` 라벨은 **본인만** 지정한다.

## 4. 보안·정보보호 규칙 (필수)
 
1. **토큰·키·비밀번호를 채팅에 입력하지 않는다.** 필요한 값은 GitHub Secrets / Cloudflare 환경변수에 본인이 직접 등록한다.
2. `.env`, `*.pem`, `*.key`, 인증 정보 파일은 커밋하지 않는다. `.gitignore`에 반드시 포함한다.
3. **회사(Riman) 내부 정보 금지**: 사내 코드, 시스템명, 내부 URL, 고객·매출 데이터, 장애 상세 내역은 글에 쓰지 않는다. 실무 경험은 일반화된 형태로만 작성한다.
4. 에이전트에 부여하는 GitHub 권한은 이 저장소 하나, Contents/Pull requests 쓰기로 최소화한다.
5. 회사 PC 사용 시 회사 보안 정책(외부 서비스 로그인 허용 여부 등)을 먼저 확인한다.
6. 참고 자료의 원문을 대량 인용하지 않는다. 출처 링크와 내 말로 정리한 요약만 남긴다.

## 5. 글 작성 규칙
 
### 5.1 파일 규칙
- 경로: `content/posts/{slug}.mdx`
- slug: 영문 소문자 + 하이픈 (예: `tcp-handshake`)
- 이미지: `public/images/posts/{slug}/`
- 텍스트: 
  모든 출력(문서, 커밋 메시지, 코드 주석, 터미널 응답)에서 이모지/유니코드 심볼 금지.
  허용: `[OK]` `[FAIL]` `[!]` `->` `=>` `*` `-` `>` `+`

### 5.2 Frontmatter (필수 필드)
 
```yaml
---
title: "TCP 3-way Handshake는 왜 3번인가"
slug: tcp-handshake
category: cs             # language | database | framework | cs | architecture | devops | data | security | domain (04_카테고리.md 기준)
subcategory: Network     # 선택. 04_카테고리.md 소분류 이름 그대로 (에이전트 작성 시 항상 채움)
series: network          # 선택. 시리즈 묶음 id
seriesOrder: 2           # 선택
date: 2026-10-14
updated: 2026-10-14
status: 초안             # 초안 | 작성중 | 확인필요 | 완료 | 갱신필요 (에이전트 작성 시 항상 초안)
tags: [tcp, handshake]
summary: "한두 문장 요약"
readingTime: 10          # 분
---
```
 
### 5.2.1 상태 라벨 (status)
 
| 라벨 | 색 | 의미 | 지정 |
|---|---|---|---|
| `초안` | 회색 | 에이전트가 작성, 아직 손대지 않음 | 에이전트 (작성 시 자동) |
| `작성중` | 파랑 | 본인이 TODO를 채우는 중 | 본인 |
| `확인필요` | 노랑 | 사실 확인·실험이 필요한 내용이 남음 | 본인 또는 에이전트 |
| `완료` | 초록 | 본인이 직접 검토하고 다듬음 | 본인만 |
| `갱신필요` | 빨강 | 버전 변경 등으로 내용이 오래됨 | 본인 |
 
- 모든 글은 상태와 무관하게 게시된다. 라벨은 숨김이 아니라 표시 용도다.
- 글 목록 카드와 글 상세 제목 위에 라벨을 표시하고, 글 목록에서 상태별 필터를 제공한다.
- CMS에서는 드롭다운으로 선택한다.

### 5.3 본문 구조 (고정 템플릿)

글의 중심은 기술 설명(1~6)이다. 면접 연결(7)은 본문을 바탕으로 마지막에 덧붙이는 섹션이며, 본문만 읽어도 하나의 기술 글로 완결되어야 한다.

1. **들어가며** — 이 글에서 다루는 문제, 왜 알아야 하는지
2. **핵심 개념** — 정의와 동작 원리. 3~5개 섹션, 섹션마다 "왜"를 설명
3. **동작 살펴보기** — 예제 코드, 흐름도, 시각화 컴포넌트
4. **실무 관점** — 트레이드오프, 흔한 실수, 설정값 (실무 사례는 일반화된 형태로만)
5. **직접 해본 것** — 코드 실행, 실험, 실무 사례(일반화). 에이전트는 `<!-- TODO: 직접 확인 -->` 자리만 비워둔다
6. **정리** — 3~5줄 요약
7. **면접으로 연결하기**
   - 7-1 질문이 나오는 흐름 — 어떤 질문·맥락에서 이 주제로 넘어오는지
   - 7-2 대표 질문과 답변 골격 — 30초 안에 말할 수 있는 분량
   - 7-3 예상 꼬리질문 — 3~5개, 질문마다 답변 포인트 한 줄
   - 7-4 스스로 점검 — 체크리스트 (선택)
8. **연계 학습** — 선행 주제(먼저 알아야 할 것) / 심화 주제(이어서 볼 것). 블로그에 이미 있는 글이면 링크
9. **참고 자료** — 공식 문서, RFC 등 1차 출처 우선

- 화면 표시: `## 면접으로 연결하기` 섹션부터 글 끝까지(7~9)는 섹션마다 접힌 아코디언으로 표시되고, 클릭하면 펼쳐진다. 이 동작은 h2 제목이 정확히 "면접으로 연결하기"일 때만 적용되므로 제목 문구를 바꾸지 않는다. (코드: `lib/mdx.tsx`의 `FOLD_FROM_HEADING`)
- 표는 본문 너비에 맞춰 표시되고, 열이 많아 넘치면 표 영역 안에서만 가로 스크롤된다.
- 목차는 h2(`##`), h3(`###`) 제목으로 자동 생성된다. 넓은 화면에서는 본문 오른쪽에 스크롤을 따라오며 현재 위치를 표시하고, 좁은 화면에서는 본문 위 접이식 상자로 표시된다. 목차에 그대로 노출되므로 제목은 짧고 내용을 알 수 있게 쓴다. h4 이하는 목차에 넣지 않는다.

### 5.4 에이전트 초안 작성 원칙
- "직접 해본 것"(5)과 "답변 골격"(7-2)의 내 말로 정리하는 부분은 **비워두고 TODO 표시**한다. 본인이 채워야 면접에서 설명 가능하다. 에이전트는 7-2에 답변에 들어갈 핵심 포인트만 적는다.
- 7번 면접 연결은 본문에서 설명한 내용 안에서만 작성한다. 본문에 없는 내용을 면접 섹션에만 넣지 않는다.
- 확실하지 않은 내용은 `<!-- 확인 필요: ... -->` 주석으로 표시한다.
- 버전·스펙 수치는 출처를 함께 적는다.
- `subcategory`는 항상 채운다. 값은 04_카테고리.md 해당 대분류의 소분류 이름을 그대로 쓴다.
- 과장된 수치, 출처 없는 통계, 가상의 후기를 넣지 않는다.

### 5.5 인터랙티브 시각화 규칙
 
- 위치: `components/viz/{ComponentName}.tsx` (React + SVG, 외부 라이브러리 추가 없이)
- **문구·데이터는 MDX에, 동작·디자인은 코드에** 둔다.
  - 라벨, 단계 설명, 순서, 수치 등은 컴포넌트 props로 MDX 안에 작성한다 → CMS에서 바로 수정 가능
  - 컴포넌트 코드에는 화면 문구를 하드코딩하지 않는다
- 예시:
```mdx
<StepViz steps={[
  { label: "SYN", desc: "클라이언트가 연결 요청" },
  { label: "SYN-ACK", desc: "서버가 요청 수락 + 자기 연결 요청" },
  { label: "ACK", desc: "클라이언트가 수락 확인" },
]} />
```
 
- 가능하면 재사용 가능한 범용 컴포넌트(단계 진행형, 비교 토글형, 상태 전이형 등)를 우선 만들고, 글마다 데이터만 바꿔 쓴다.
- 수정 경로:
| 수정 대상 | 방법 |
|---|---|
| 문구, 단계 설명, 순서, 수치 | 사이트 CMS에서 직접 수정 |
| 동작, 레이아웃, 디자인, 새 컴포넌트 | Cowork 프로젝트에서 Claude에게 요청 (프롬프트 P9) → PR 검토 후 반영 |

### 5.6 본문 강조 표기 (가독성)

핵심 키워드가 눈에 들어오도록 마크다운 강조 문법에 사이트 CSS 효과를 입힌다. 글에는 마크다운 문법만 쓰고, 색·굵기는 사이트 CSS(`app/globals.css`의 `.prose`)에서 정한다. (CMS에서 그대로 편집 가능)

| 표기 | 용도 | 화면 효과 |
|---|---|---|
| `**키워드**` | 핵심 키워드, 처음 등장하는 핵심 용어 | 굵게 + 강조색 |
| `*문구*` | 보조 강조 (주의할 점, 헷갈리기 쉬운 차이) | 기울임 없이 형광펜 밑줄 |
| `` `코드` `` | 명령어, 설정값, 함수·클래스 이름, 상태 값 | 고정폭 글꼴 + 회색 배경 |

- 강조는 문단당 1~2개로 제한한다. 강조가 많으면 오히려 핵심이 흐려진다.
- 제목(##, ###)과 표 머리글에는 강조 표기를 쓰지 않는다.
- 색만으로 의미를 전달하지 않는다. 강조를 빼고 읽어도 문장이 성립해야 한다.
- 에이전트 초안에서는 각 본문 섹션의 핵심 용어를 `**키워드**`로 표시한다.
- 주의: 닫는 `**` 바로 앞이 괄호·문장부호이고 뒤에 한글이 붙으면 강조가 적용되지 않는다. 괄호는 강조 밖으로 뺀다. 예: `**순서 번호(Sequence Number)**를` (X) -> `**순서 번호**(Sequence Number)를` (O)
 
## 6. 코드 변경 원칙
 
- 요청받은 범위만 수정한다. 대규모 리팩터링·의존성 추가는 사전 승인 후 진행한다.
- 변경 시 **변경 파일, 변경 내용, 변경 이유**를 기록한다. 기록 대상과 위치는 8장 변경 관리 분류를 따른다.
- 기존 글의 문체·구조를 유지하고, 명백한 오탈자·사실 오류만 수정한다.
- 항상 저장소의 최신 파일을 기준으로 작업한다. 이전 대화 내용은 참고만 한다.

## 7. 응답 규칙
 
- 기본 언어: 한국어 (기술 용어는 영어 병기 가능)
- 작업 완료 시: 무엇을 했는지 한두 줄 + 본인이 할 일(있다면) 명시
- 사실 / 추정 / 미확인을 구분해서 말한다.

|---|---|---|---|
| A. 규칙 변경 | 다음 세션이나 예약 작업(P8)이 알아야 하는가 | frontmatter 필드, 카테고리·소분류, 글 템플릿, 권한·보안 규칙, 프롬프트 | 규칙 문서 본문 수정 + 문서 하단 변경 이력 + `CHANGELOG.md` + Cowork 프로젝트 문서 동기화 |
| B. 지속 변경 | 사이트 동작·모양이 계속 바뀌고, 되돌릴 때 이유가 필요한가 | 메뉴 구조, 시각화 컴포넌트, 배포 워크플로, 의존성 추가 | `CHANGELOG.md` 한 줄 + 커밋 메시지 |
| C. 일회성·사소 | A, B에 해당하지 않음 | 오탈자, 여백·색 미세 조정, 실험 후 되돌린 변경, 글 본문 수정 | 커밋 메시지만 |

- 글(`content/posts`)은 `post:` 커밋과 `docs/topic-history.md` 기록으로 관리한다.
- 분류가 애매하면 에이전트가 분류를 제안하고 본인이 정한다.
- 규칙은 반드시 .md 문서에 작성한다. 대화에서만 정한 규칙은 다음 세션에 적용되지 않는다.

### 8.2 기록 시작 시점

- `CHANGELOG.md`는 저장소 첫 push 상태를 기준선으로 하고, 그 이후의 A·B 변경부터 기록한다. 첫 push 전 작업은 "초기 구축" 한 줄로 둔다.
- 규칙 문서(기본지침, 카테고리, 프롬프트)의 하단 변경 이력 표는 문서 생성 시점부터 A 변경을 계속 기록한다.

### 8.3 기록 형식

- `CHANGELOG.md` 한 줄: `| 날짜 | 분류 | 변경 파일 | 변경 내용 | 이유 |`
- 규칙 문서 하단 변경 이력: `| 날짜 | 변경 내용 | 이유 |`
- 커밋 메시지 접두어: `rule:`(A), `feat:` `fix:` `chore:`(B 또는 C), `style:`(C), `post:`(글)

### 8.4 저장소와 Cowork 프로젝트 동기화

| 저장소 (git 이력) | Cowork 프로젝트 | 동기화 방법 |
|---|---|---|
| `docs/guidelines.md` | `claude/01_기본지침.md` | 에이전트가 양쪽 모두 수정 |
| `docs/categories.md` | `04_카테고리.md` | 에이전트가 양쪽 모두 수정 |
| `docs/prompts.md` | `02_프롬프트.md` | 에이전트가 양쪽 모두 수정 |
| (없음) | `03_작업진행계획.md` | 프로젝트에만 둔다 (진행 체크용) |

- 프로젝트 문서 위치: 기본지침만 `claude/` 폴더(`claude/01_기본지침.md`), 나머지(`02_프롬프트.md`, `03_작업진행계획.md`, `04_카테고리.md`)는 프로젝트 최상위에 있다.
- 양쪽 내용이 다르면 저장소 문서를 기준으로 맞춘다. 저장소에 아직 반영되지 않은 경우에는 프로젝트 문서를 기준으로 한다.
- 카테고리·소분류를 바꾸면 사이트 코드의 `lib/taxonomy.ts`도 함께 수정한다.
- 주간 점검(P6)에서 양쪽 문서가 같은지 확인한다.
- 프로젝트 지침(Cowork 설정)은 본인만 수정한다. 에이전트는 지침 문구 변경이 필요하면 제안만 한다.

### 8.5 규칙 변경 절차

1. 에이전트가 "변경 전 -> 변경 후 -> 이유" 형식으로 제안한다.
2. 본인이 승인한다.
3. 저장소 문서는 PR(브랜치 `rule/{요약}`)로, 프로젝트 문서는 직접 수정하고, 8.3 형식으로 이력을 남긴다.
4. 에이전트는 본인이 할 일(PR 병합, 프로젝트 지침 고정 문구 변경이 필요한 경우 등)을 마지막에 안내한다.
